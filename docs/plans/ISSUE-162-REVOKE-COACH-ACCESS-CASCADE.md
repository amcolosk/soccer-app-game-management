## Goal

`revokeCoachAccess` (`src/services/invitationService.ts`) today writes only `Team.coaches`. It does not mirror `accept-invitation`'s add-side backfill, so a revoked coach keeps full `allow.ownersDefinedIn('coaches')` read/write on every `TeamRoster`, `FieldPosition`, `Game`, and `TeamInvitation` record for that team, and can even reverse the revocation outright by re-accepting their own old invitation. This plan makes revocation a real, server-side, cascading operation, with the same reliability guarantees (`accept-invitation`'s optimistic-concurrency retry, generalized) as the add-side.

**Definition of done:** `revokeCoachAccess` is a Lambda-backed custom mutation. It removes the target user from `Team.coaches`, and unconditionally sweeps that removal onto every team-scoped record for that team — `TeamRoster`, `FieldPosition`, `Game`, and `TeamInvitation` (both the `coaches` field, and, separately, expiring any of the target's own already-`ACCEPTED` invitations **and** any still-`PENDING` invitations to that same email, closing the reversibility hole below for any target with at least one `ACCEPTED` invitation row on this team — see the two named residual risks (F3, F4) below for the cases this does not close). `Player`, `Formation`, and `FormationPosition` are explicitly **not** swept in this slice (see "Central design finding" — no provenance field makes correct revocation undecidable for these three, and incorrect removal is irreversible personal-library data loss). `npm run gate:commit` is green; the existing issue-#162 reproducer test in `invitationService.test.ts` is replaced with real coverage of the new mutation-backed shape; a new `amplify/functions/revoke-coach-access/handler.test.ts` exercises the Lambda directly, including the concurrent-revoke abort case and both `TeamInvitation` reversibility-close cases (accepted-and-still-linked, and pending duplicate).

**Scope of the "complete cutoff" claim:** revocation is a real, complete cutoff of a team's own operational data (roster, live lineup positions, games, invitations). For the invitation-reversibility hole specifically, this cutoff is complete **for any coach who has at least one `ACCEPTED` `TeamInvitation` row on this team** — both their own `ACCEPTED` invitation and any still-`PENDING` duplicate to the same email are closed by the same targeted status transition (see "Central design finding" §3). It is **not** complete for a coach with no `ACCEPTED` invitation row on this team (team creators; anyone whose `ACCEPTED` row was separately deleted) — there is no email to derive, so a stray `PENDING` invitation to their address survives revocation as a working self-restore path (named residual risk F3), and even for a coach who does have an `ACCEPTED` row, a true sub-second concurrent accept-vs-revoke race on that same invitation can still land them back on the team (named residual risk F4). It does **not** retroactively remove access to `Player`/`Formation`/`FormationPosition` records the revoked coach still has via `coaches` on those rows, and does **not** touch `Substitution`/`LineupAssignment`/`PlayTimeRecord`/`Goal`/etc. — all are explicit, documented residual risks (see "Explicit scope statement" and Docs changes), not gaps in what this plan actually promises.

## Central design finding (read before anything else)

The issue's suggested fix says the sweep must be "scoped to that team only, since players/formations can be shared across teams." Read together with what `accept-invitation`'s idempotent-repair branch actually does, this changes the shape of the fix in three ways, not one:

### 1. Why `Player`/`Formation`/`FormationPosition` are excluded entirely, not conditionally swept (Critical 3)

`Player.create()` and `Formation.create()` (`src/components/Management.tsx`, `src/services/demoDataService.ts`) set `coaches: [currentUserId]` with **no team linkage and no provenance field** — `amplify/data/resource.ts` has no `createdBy`/`ownerId` on either model. The original draft's conditional rule ("remove U from this record's `coaches` only if no other team of U's still explains their presence") misses the single most common legitimate case: **U created that player/formation themselves, independent of any team.**

Concretely: coach U creates Team A, formation F, and 15 players; invites V; V accepts; V later revokes U (permitted — any coach may revoke any coach, including the owner, per `assign-team-owner`'s already-accepted tradeoff). A scan finds no other team of U's using those players/that formation (U may not coach any other team at all), so a conditional sweep would strip U from all of them — U's entire player library and custom formation vanish from U's account, with no recovery path. This directly contradicts `docs/SHARING-PERMISSIONS.md`'s existing stated guarantee that a coach keeps "their own created players and formations (even if not on this team)."

**Decision:** do not sweep `Player`, `Formation`, or `FormationPosition` at all in this slice. Fixing this correctly would require adding a `createdBy` field to `Player`/`Formation`, never stripping the creator, and deciding how legacy rows with no `createdBy` are handled — a data-model change with its own migration-risk profile, materially larger than issue #162 as filed. Recorded as a **named residual risk** in `docs/SHARING-PERMISSIONS.md` (Docs changes below): a revoked coach who is not the sole "owner" of a shared `Player`/`Formation` retains read/write access to it via `coaches` until/unless a future slice adds provenance tracking.

Because this rule is dropped, the cross-team `remainingTeams` scan the original draft needed to support it (previously handler step 8) is also dropped — there is no more cross-team lookup anywhere in this design (this is what makes architecture review's Major 4 moot).

### 2. Team-scoped models: unconditional sweep, now including `FieldPosition` and `TeamInvitation`

`TeamRoster`, `Game`, `FieldPosition`, and `TeamInvitation` are each team-scoped by construction (`teamId` is a single required reference on all four) — removing the revoked user from every row of these four for *this* team is always correct; no other team's access is affected. `FieldPosition` is added in this revision (architecture review Minor 7): it gates read/write on a team's live lineup-position rows — the runtime state `LineupAssignment`/`Substitution`/`PlayTimeRecord` actually key off (CLAUDE.md, "Two position models") — and costs nothing extra to sweep given the same generic `updateRecordCoachesWithRetry` helper already being used for `TeamRoster`. Leaving it out while sweeping `TeamRoster` would be an arbitrary asymmetry, not a considered exclusion.

### 3. `TeamInvitation`: sweep AND a targeted status transition (closes Critical 1 and Major 1), run before the `Team.coaches` write (Major 2)

`TeamInvitation` needs two different treatments:

1. **`coaches` field** — swept unconditionally, identical shape to `TeamRoster` (each row already carries `coaches`, copied from `Team.coaches` at invitation-creation time — `invitationService.ts:37` — and never re-synced since; this closes that for the revoke direction the same way this plan does for the other team-scoped models). This step's position in the handler is unchanged from round 1 — it stays grouped with the other unconditional child-record sweeps (file #4, step 10).
2. **Status transition — the actual fix for reversibility, now covering both `ACCEPTED` and `PENDING` rows.** `accept-invitation/handler.ts:497-533`'s non-`PENDING` branch treats an invitation that is already `status: 'ACCEPTED'` with `acceptedBy` equal to the caller as an idempotent "repair": it unconditionally re-appends the caller into `Team.coaches` (**not** archived-gated, does not consult `coaches` at all) and re-runs the full add-side backfill. Left alone, this means a revoked coach U can call `acceptInvitation` again with their own original (still-`ACCEPTED`) invitation ID and be fully re-granted, including everything this plan's sweep just removed — making "revocation is a complete cutoff" false.

   **Fix**, mirroring `archive-team/handler.ts:135-165`'s pending-invitation-expiry pattern: scan `TeamInvitation` for `teamId = :teamId`, projecting `['id', 'coaches', 'status', 'acceptedBy', 'email']` (`email` added since round 2 — round 1's projection omitted it; `status` requires the `#status` reserved-word alias fix from architecture review round 3 (F1) — see file #1 and file #4 step 3 for the exact call shape). From that one scan:
   - For rows where `acceptedBy = targetUserId AND status = 'ACCEPTED'`, conditionally update each to `status = 'EXPIRED'` (guarded by `status = :acceptedStatus`, ignoring `ConditionalCheckFailedException` as "already transitioned" — same per-item pattern as `archive-team`). `EXPIRED` already exists in the `status` enum (`amplify/data/resource.ts:416`) — **no schema change needed.**
   - **Round 1 wrongly left still-`PENDING` invitations to the target's email untouched, on two grounds that don't hold up (Major 1):** (a) it assumed a `PENDING` duplicate was hypothetical and re-creatable at will anyway — but duplicate `PENDING` invitations to the same email/team are routine, not hypothetical: `sendTeamInvitation` has no duplicate-invite guard, and `accept-invitation/handler.ts:470-473`'s own comment confirms this is an expected, already-handled case on the accept side. Concrete failure this leaves open: coach A invites B twice (first email went to spam); B accepts invitation #1; A revokes B; B then clicks the still-`PENDING` invitation #2's link and is fully restored via `accept-invitation`'s **ordinary `PENDING`-accept path** — no repair-branch involved at all, no coach action required, "revocation is a complete cutoff" false again, just via a different invitation row. (b) it assumed matching by email required `AdminGetUser`/Cognito — but `TeamInvitation.email` is a required field already present on every row, and the same `TeamInvitation` scan being added for the `ACCEPTED → EXPIRED` transition already reads every row for this team; the target's email can be read directly off the matched `ACCEPTED` row(s) (`acceptedBy === targetUserId`) with zero extra calls and no `USER_POOL_ID`/IAM wiring.

     **Fix:** derive `targetEmail = normalizeEmail(email)` from the `ACCEPTED` row(s) matched above. If a `targetEmail` was derived, also conditionally expire every `PENDING` row on this team whose `normalizeEmail(email) === targetEmail`, using the identical conditional pattern (guarded by `status = :pendingStatus`, ignoring `ConditionalCheckFailedException`) — this is exactly `archive-team/handler.ts:145-165`'s own pending-invitation-expiry loop, reused for a per-email filter instead of "every `PENDING` row on the team."

     **Named residual risk (F3), stated honestly rather than as "nothing to close":** if no `ACCEPTED` row exists for the target on this team (e.g. the target was the team's creator and never went through the invitation flow, or their `ACCEPTED` row was separately deleted), there is no non-Cognito source for their email in that case — closing it fully would require the `AdminGetUser`/`USER_POOL_ID` wiring this plan otherwise avoids — so no `PENDING`-by-email sweep can run for them. This is **not** "nothing to close": `sendTeamInvitation` has no already-a-coach guard, so a co-coach could still (by mistake or otherwise) invite the target's own email while they're already a coach, creating a `PENDING` row with no corresponding `ACCEPTED` row. Net effect: a coach with no `ACCEPTED` invitation row on this team has no derivable email for the PENDING sweep, so any stray `PENDING` invitation to their address is **not** expired by revocation and remains a working self-restore path via the ordinary `PENDING`-accept flow. Accepted as a residual risk, not built around in this slice — see "Risks and edge cases" and `docs/SHARING-PERMISSIONS.md`.

   Once `EXPIRED`, `accept-invitation`'s non-`PENDING` branch falls through to `toInvitationStateError('EXPIRED')` ("Invitation has expired") instead of repairing membership, and its `PENDING` branch's own status-guarded conditional write simply fails closed. (Confirmed against the actual UI: `src/components/InvitationAcceptance.tsx` reads `invitation.status` directly and only renders an "Accept" button when `status === 'PENDING'`; once `EXPIRED`, the button never even renders, so this is airtight from the UI as well as from a direct mutation call.)

   **Ordering — must run before the `Team.coaches` write (Major 2).** Round 1 placed this status transition last in the handler algorithm, after the `Team.coaches` write and all four child-record sweeps. That reopens the exact reversibility hole Critical 1 was meant to close, for the entire window between the `Team.coaches` write and this (possibly failing/delayed) step: if the handler times out or fails after removing the target from `Team.coaches` but before expiring their invitation(s), `accept-invitation/handler.ts:497-533`'s repair-branch condition (`attribute_not_exists(coaches) OR NOT contains(coaches, :coachId)`) now **passes** (the target was just removed), so the target can re-run `acceptInvitation` during that window and be fully re-granted — undoing the revoke. **Fix:** the `TeamInvitation` scan and both status transitions now run immediately after the caller-membership/archived-team check (`assertTeamAccess`) and before the `Team.coaches` write — see file #4's renumbered algorithm. **This closes the crash/timeout/partial-failure version of the window described above** (the handler dies or is delayed between the two writes). **Named residual risk (F4), not closed by this reorder:** a true sub-second concurrency race — the target calls `acceptInvitation` for a still-`PENDING` invitation at almost exactly the same moment a coach calls `revokeCoachAccess` on them — can still let the target land back on the team. Concretely: revoke's `TeamInvitation` scan (step 3) reads the invitation as still `PENDING` (about to be accepted); the accept lands afterward as an ordinary successful `PENDING → ACCEPTED` transaction; revoke's own `PENDING`-expiry conditional write (step 5) then fails harmlessly with `ConditionalCheckFailedException` (correctly treated as "already transitioned, someone else updated it"); but revoke's step 4 (`ACCEPTED → EXPIRED`) was computed from the earlier stale scan and never sees the invitation's new `ACCEPTED` status, so it's never expired. Net effect: revoke's `Team.coaches` write still removes the target, but the target's freshly-accepted membership isn't cut off by the invitation-expiry step, and no second post-write expiry pass is added to close this — it is a narrow, accepted residual risk given how rare simultaneous accept-and-revoke on the same invitation is in practice, not something this plan builds additional wiring to close. See `docs/SHARING-PERMISSIONS.md` for this recorded as a named residual risk, and file #6's coverage list for how this is tested (as a documented known gap, not asserted-closed).

   **Resulting tradeoff, accepted and documented, not a new gap:** if the `Team.coaches` write subsequently `abort`s (Critical 2's zero-coaches guard, or the rarer concurrent caller-membership-abort case), the target's invitation(s) are left `EXPIRED` while the target remains a full coach — no access is lost, since the `Team.coaches` write never took effect. The only effect is that the invitation's own drift-repair path for an already-granted membership is now closed too, which is harmless: that repair path exists to restore membership that's supposed to still be there, and here it still is. See file #4 step 6 for where this is called out in the algorithm itself.

This is also why `accept-invitation` never had to solve any of this: its backfill is purely additive (union) and its idempotent-repair branch only ever re-grants what the caller is re-asserting for themselves — it can never accidentally revoke someone's legitimate access, nor does its own idempotency loop back around into a "was this access actually still valid" question. Revocation is the first place both asymmetries matter, and it's the main reason this can't be a byte-for-byte copy of the accept-side Lambda.

## Explicit scope statement

**In scope (the sweep targets):**
- **Unconditional `coaches` sweep:** `TeamRoster`, `FieldPosition`, `Game`, `TeamInvitation` — each team-scoped by a required `teamId`.
- **Targeted status transition:** `TeamInvitation` rows where `acceptedBy = targetUserId AND status = 'ACCEPTED'` → `EXPIRED`, **and** (Major 1) any `PENDING` row on this team whose email normalizes to the same email as those matched `ACCEPTED` row(s) → `EXPIRED` — both run before the `Team.coaches` write (Major 2, see "Central design finding" above).

This is a deliberately different (and, per Criticals 1/3, corrected) set from the original draft's five `accept-invitation`-mirrored models. `accept-invitation` itself is not changed to match this new set — file #3 below remains a behavior-preserving refactor only, not a scope change.

**Out of scope: `Player`, `Formation`, `FormationPosition`.** See "Central design finding" §1 above (Critical 3) — no provenance field makes correct revocation undecidable for these three, and incorrect removal is irreversible personal-library loss. Recorded as a residual risk in `docs/SHARING-PERMISSIONS.md`, not silently absorbed or dropped.

**Out of scope: `Substitution`, `LineupAssignment`, `PlayTimeRecord`, `Goal`, `PlayerAvailability`, `GamePlan`, `PlannedRotation`, `GameNote`, `QueuedSubstitution`.** All nine are `allow.ownersDefinedIn('coaches')` with no field-level lockdown and no sweep on the add side either (confirmed by reading `accept-invitation/handler.ts` in full — it only backfills `TeamRoster`, `Player`, `Formation`, `FormationPosition`, `Game`). Same reasoning as the original draft's four: there is no existing "coaches stays in sync" contract for these to mirror on the revoke side; fixing it requires deciding how all nine should be kept in sync on *both* accept and revoke, a design question bigger than #162 as filed, and one that should be evaluated together, not patched one-sided here. Listed explicitly (architecture review Minor 7) rather than a partial list, since these are genuinely all in the same bucket.

**Strengthened residual-risk wording (Minor 7):** `allow.ownersDefinedIn('coaches')` without field-level lockdown includes `delete`, not just `read`/`update`. `PlayTimeRecord`, `LineupAssignment`, and `Substitution` specifically are, per CLAUDE.md, "the source of truth for all play-time math ... and the fair-rotation algorithm," and "meant to move together" with each other. A revoked coach who's still listed in these rows' `coaches` retains the ability to **delete** them individually — not just view them — which can desynchronize that trio for a team they're no longer supposed to touch at all. This is recorded verbatim in the new `docs/SHARING-PERMISSIONS.md` residual-risk bullet (Docs changes below), not softened to "retains access."

**Out of scope: the owner-revoked-then-reclaimed hijack scenario.** Per the issue's own instructions, this is accepted and tracked separately (`TEAM-ARCHIVE-STEP1-BACKEND-WIRING.md` Required Follow-Up #7, `TEAM-ARCHIVE-STEP10-E2E-AND-DOCS.md`). This plan does not add an owner guard to revocation. See "Risks and edge cases" for why the new Lambda is nonetheless a natural future home for that follow-up, without implementing it now.

**In scope, beyond the issue's literal text: a guard rejecting revocation that would leave a team with zero coaches.** Today's client function has no such guard. A team with an empty `coaches` array becomes permanently inaccessible — `allow.ownersDefinedIn('coaches')` gates *read* as well as write, so no one, including `assignTeamOwner` (which itself requires `contains(coaches, :callerSub)`), could ever recover it. This is a distinct, narrower guard than the out-of-scope "owner" guard above (it doesn't care who the owner is, only that at least one coach remains). In this revision it is implemented as an `'abort'` outcome inside the `Team`-level retry strategy itself, re-checked on every retry attempt — not a one-time pre-check — see Critical 2's fix below.

## Architecture decision: Lambda-backed custom mutation (not client-side)

**Decision:** Replace `revokeCoachAccess`'s current plain `client.models.Team.get`/`Team.update` implementation with a new Lambda-backed custom mutation `revokeCoachAccess`, mirroring `acceptInvitation`/`archiveTeam`/`restoreTeam`/`assignTeamOwner`'s existing pattern (`allow.authenticated()` at the schema level; the real authorization check lives inside the handler).

**Rationale:**
1. **The sweep needs multi-record, retry-safe writes.** `accept-invitation`'s `updateRecordCoachesIfNeeded` exists precisely because a plain single-shot `update()` racing against a concurrent write on the same record silently loses data. The revoke sweep has the identical shape (many records, each independently racy) and needs the identical optimistic-concurrency retry, not a client-side loop of individual `client.models.X.update()` calls (which the current reproducer test naively assumes — see "Reconciling the reproducer test" below).
2. **A client-driven sweep cannot be trusted to enforce the zero-coaches/caller-membership invariants under concurrency.** Doing this from the browser would mean trusting client-computed removal decisions on records the client will then directly patch with `allow.ownersDefinedIn('coaches')`-gated writes; a buggy or compromised client could just as easily strip access it shouldn't, or fail to strip access it should, with no server-side authority to check its work — and, per Critical 2 below, would have no reliable way to close the concurrent-double-revoke race at all.
3. **Authorization boundary changes, and must be explicitly re-created.** Today, `revokeCoachAccess`'s only implicit protection against a non-coach caller is that AppSync's model-level `allow.ownersDefinedIn('coaches')` grant on `Team.update` already rejects a caller not in `coaches`. Moving to a Lambda (which runs with elevated IAM, bypassing that model-level grant) means **the handler itself must re-implement the caller-membership check** before any write — exactly the pattern `assignTeamOwner`/`archiveTeam` already establish. This is a required correctness/security item for this plan, not optional hardening — omitting it would let any authenticated user revoke any coach from any team.
4. **Consistent with the app's own precedent.** Every other "must touch multiple coach-scoped records reliably" operation in this codebase (`accept-invitation`, `archive-team`'s pending-invitation sweep) is already Lambda-backed. A client-side revoke would be the only asymmetric exception.

**Not fully atomic, and that's an accepted, pre-existing pattern, not a new gap:** like `accept-invitation`, the `Team.coaches` write is the authoritative, immediately-consistent step; the child-record sweep that follows is best-effort with per-record optimistic-concurrency retry (3 attempts, matching `updateRecordCoachesIfNeeded`), not a single all-or-nothing transaction. DynamoDB's 100-item `TransactWriteItems` cap makes true cross-record atomicity infeasible for a team with many games/roster rows anyway — `accept-invitation` made the same call for its own backfill. Ordering matters here specifically because revocation is a "cut off access" operation: writing `Team.coaches` first (immediately after it, ahead of the `TeamRoster`/`FieldPosition`/`Game`/`TeamInvitation.coaches` sweeps) means the top-level relationship is severed correctly even if the child sweep is still catching up (mirrors, and is arguably *more* justified than, the equivalent ordering already accepted in `accept-invitation`). **One exception, deliberate (Major 2):** the `TeamInvitation` `ACCEPTED → EXPIRED` / `PENDING`-by-email status transitions are *not* part of that "child sweep" ordering — they run **before** the `Team.coaches` write, not after, because leaving that window open even briefly after `Team.coaches` is already cut would reopen Critical 1 for the crash/timeout/partial-failure case. This reorder closes that failure-mode window; it does not close a true sub-second concurrent accept-vs-revoke race on the same invitation, which remains a documented, accepted residual risk (F4). See "Central design finding" §3 and file #4's renumbered algorithm.

**Concurrent-revoke safety (Critical 2 — fixed, not just re-created as a pre-check):** the original draft's `Team`-level guards (caller-membership, zero-coaches) were one-time pre-checks performed before entering the retry loop, then the loop only recomputed the *removal itself* on conflict — not the guards. That leaves a real orphaning window: with `Team.coaches = [A, B]`, `A` revokes `B` and `B` revokes `A` concurrently; both read `[A, B]` and both pass their own pre-check (each thinks one coach will remain); `A`'s write commits first → `[A]`; `B`'s write then hits `ConditionalCheckFailedException`, and a naive retry that only recomputes the removal (not the guards) re-reads `[A]`, recomputes `remove(A)` → `[]`, and writes it — `allow.ownersDefinedIn('coaches')` gates read *and* write, and `assignTeamOwner` itself requires `contains(coaches, :callerSub)`, so the team becomes permanently unrecoverable by anyone.

**Fix:** the shared retry helper's strategy contract changes from a plain `computeNextCoaches: (current) => string[] | undefined` function to a discriminated result — `'write' | 'skip' | 'abort'` — evaluated **fresh on every retry attempt**, not just the first (see file #1 for the exact type). For the `Team`-level write specifically, the strategy closure re-checks all three invariants against the freshly re-read record on every attempt: caller (`callerSub`) still present in `coaches` → otherwise `abort`; target still present → otherwise `skip` (idempotent success); removing the target would still leave `coaches` non-empty → otherwise `abort`. Walking the race above through the fix: `B`'s retry re-reads `[A]`, re-evaluates the strategy, finds `callerSub` (`B`) is no longer present → `abort`s with "Access denied: caller is not a coach on this team" instead of blindly writing `[]`. This mirrors how `archive-team/handler.ts:106-108` and `assign-team-owner/handler.ts:81` already close the equivalent TOCTOU with a write-time `contains(coaches, :callerSub)` clause instead of relying on a one-time pre-check — this plan generalizes the same idea into the shared retry helper so every swept table gets it "for free."

## File-by-File Changes

### 1. `amplify/functions/shared/coachArraySync.ts` (new)

Extracts the generic, reusable primitives from `accept-invitation/handler.ts` into a shared module — this is the concrete trigger for Required Follow-Up #6 in `TEAM-ARCHIVE-STEP1-BACKEND-WIRING.md` ("extract `isConditionalCheckFailed`/`scanAll` ... once a further handler needs either"), extended slightly further since both handlers need the same conditional-retry write shape, not just the scan helper.

Exports:
- `isConditionalCheckFailed(error)` — moved verbatim from `accept-invitation/handler.ts`.
- `normalizeEmail(value: string | undefined | null): string` — moved verbatim from `accept-invitation/handler.ts` (this revision — Major 1: the new revoke handler now needs it too, for the `PENDING`-by-email `TeamInvitation` sweep in file #4 steps 4–5; `accept-invitation/handler.ts` keeps using it for its own email-match checks via the shared import, no behavioral change there).
- `getRecordById<T>(docClient, tableName, id, projectionFields, extraExpressionAttributeNames?: Record<string, string>)` — moved verbatim, **extended this revision (F1, architecture review round 3):** accepts an optional `ExpressionAttributeNames` map, merged into the command alongside the existing internally-generated `{ '#field': fieldName }` alias (the internal `#field` alias always wins on collision — callers only ever use the new parameter for *projection* aliases, never to rename the lookup key).
- `scanByField<T>(docClient, tableName, fieldName, fieldValue, projectionFields, extraExpressionAttributeNames?: Record<string, string>)` — moved verbatim, same new optional parameter as `getRecordById`. **Required fix (F1 — Major, architecture review round 3):** `ProjectionExpression` is still built as a naive `projectionFields.join(', ')` with no automatic aliasing. Any caller passing a DynamoDB reserved word (e.g. `'status'`) as a raw projection field name causes `ValidationException: Attribute name is a reserved keyword; reserved keyword: status` on every call, 100% of the time, in a deployed environment — and since this plan's tests mock `@aws-sdk/lib-dynamodb` directly, no test would catch this unless it's asserted for directly (see file #2). This module does **not** auto-detect reserved words; the caller is responsible for aliasing. Any projection field that's a reserved word must be passed as `'#status'` in `projectionFields`, with `{ '#status': 'status' }` supplied via `extraExpressionAttributeNames` — see file #4's `TeamInvitation` scan call site (step 3), the one place this repo currently needs it. (Note: distinct from `amplify/functions/shared/dynamo.ts`'s `scanAll`, which takes an arbitrary filter expression rather than a single field/value pair. Not consolidated in this slice — same "not this slice" reasoning already used for `teamAccess.ts` vs. the older `*Safe` handlers; flagged as a follow-up, not blocking.)
- `withBoundedConcurrency<T, R>(items, concurrency, fn)` — moved verbatim.
- `updateRecordCoachesWithRetry<T extends { id: string; coaches?: string[] }>(docClient, tableName, record, strategy, updatedAtIso, retryReadProjection?: string[])` — **generalized** version of `accept-invitation`'s `updateRecordCoachesIfNeeded`. Per architecture review Critical 2, the contract is **no longer** just `computeNextCoaches: (current) => string[] | undefined` — it is now:

  ```ts
  type CoachesStrategyResult =
    | { action: 'write'; next: string[] }
    | { action: 'skip' }
    | { action: 'abort'; reason: string };

  type CoachesStrategy = (current: string[] | undefined) => CoachesStrategyResult;
  ```

  The retry loop calls `strategy(latestRecord.coaches)` **at the top of every attempt** (up to 3), not just before the first write attempt. This is the mechanism that closes Critical 2 (see "Concurrent-revoke safety" above): every retry re-evaluates the strategy against a freshly re-read record, so an invariant that was true on attempt 1 but has since changed (e.g. the caller themselves was concurrently revoked) is caught on attempt 2, not blindly retried against a stale assumption.
  - `'write'` → attempts a conditional `UpdateCommand` pinned to the exact `latestRecord.coaches` snapshot the strategy was evaluated against (`attribute_not_exists(coaches) OR coaches = :expectedCoaches`, same shape as `accept-invitation`'s existing write) — on `ConditionalCheckFailedException`, re-reads via `GetCommand` and loops (up to 3 attempts total; exhausting all 3 throws `Failed to update coaches after concurrent update retries`, worded per call site, matching `accept-invitation`'s existing precedent for this failure mode). **Retry re-read projection (F2 — Major, architecture review round 3):** the `GetCommand` used for this re-read is projected using the new `retryReadProjection` parameter when supplied (`ProjectionExpression` built the same way as `getRecordById`); when omitted, the re-read fetches the **full, unprojected record**. Child-record callers (`TeamRoster`/`FieldPosition`/`Game`/`TeamInvitation` — all of which only ever need `id`/`coaches` back) pass `['id', 'coaches']`, unchanged from before. The `Team`-level call (file #4 step 6) now **omits this parameter**, so its retry re-read always returns the full `Team` record — this is required because that call's `record` is returned to the client as-is as the mutation's `a.ref('Team')` response, and `Team.name` is `.required()` in the schema; an `['id', 'coaches']`-projected stub returned as a `'skip'` result (e.g. after a concurrent-revoke conflict resolves to "target already removed by the other attempt") would otherwise fail AppSync's non-nullable-field validation and surface a spurious client-visible error for a revoke that actually fully succeeded. **No-record-found case, newly specified (F2):** if a retry re-read's `GetCommand` finds no record at all (the row was deleted between attempts), the helper throws `Failed to re-read record during concurrent update retry — record no longer exists`, worded per call site, matching this file's existing "Failed to backfill coaches ... after concurrent update retries" error text — this case previously had no defined behavior in the discriminated-union return type.
  - `'skip'` → no write, returns success immediately. Used for: target already absent from a record's `coaches` (idempotent no-op — a retried call after a partial prior failure, or a benign double-click/race, still finishes without erroring); and, per **Minor 9**, whenever the computed next array would be *empty* on a **child** record — rather than writing `coaches: []` and making that record invisible/inaccessible to everyone with no recovery path, the sweep skips it and the handler logs a warning (see file #4). This applies uniformly to every swept child table, not just an ad hoc special case.
  - `'abort'` → throws `new Error(reason)` immediately, no retry, no further write attempted. Used by the `Team`-level strategy for the caller-membership and zero-coaches invariants. Child-record strategies never use `'abort'` — they only ever `'write'` or `'skip'` (an aborted child-record write would incorrectly fail the whole revoke for a condition that isn't actually about this operation's own authorization).

  `accept-invitation` will call this with an add/merge strategy (always `'write'` or `'skip'`, never `'abort'` — the add side has no invariant that can regress mid-retry); the new revoke Lambda calls it with a remove strategy for every swept table, including the `Team` record's own update.

  **Return shape (Minor 3 — specified explicitly, not left for the implementer to guess):**

  ```ts
  type CoachesWriteResult<T> =
    | { action: 'write'; record: T }
    | { action: 'skip'; record: T };
  // 'abort' never returns — it throws, per the bullet above.
  ```

  `record` is the latest known state of the row: for `'write'`, the `ReturnValues: 'ALL_NEW'` attributes from the successful conditional `UpdateCommand` (always the full record — unaffected by `retryReadProjection`, which only governs conflict re-reads); for `'skip'`, the most recently read record (the one the strategy was evaluated against — either the record passed in, or the result of the most recent retry re-read, whose completeness now depends on `retryReadProjection` per the F2 fix above). Callers that need "what does this row look like now" as a **complete** record (file #4 step 6's `Team`-level call, whose result is returned to the client as the mutation's `a.ref('Team')` response) call `updateRecordCoachesWithRetry` **without** `retryReadProjection` and use `result.record` directly; callers that only care whether a write happened (all the child-record sweep steps) pass the narrow `['id', 'coaches']` projection and can ignore `record` and branch on `action` alone for logging.

### 4. `amplify/functions/revoke-coach-access/handler.ts` (new)

New Lambda, `Schema['revokeCoachAccess']['functionHandler']`. High-level algorithm (renumbered this revision — Major 2 moves the `TeamInvitation` status transitions ahead of the `Team.coaches` write):

1. Resolve `callerSub` from `event.identity` (same `AppSyncIdentityCognito` pattern as `archive-team`/`assign-team-owner`). No authenticated user → error.
2. **Read + membership + archived-team gate, via the shared helper** (architecture review Minor 5): `assertTeamAccess(docClient, teamTable, teamId, callerSub, { requireActive: true, archivedMessage: "Cannot revoke coach access for an archived team. Restore the team first." })`. This replaces the original draft's hand-rolled `GetCommand` + membership check with `amplify/functions/shared/teamAccess.ts`'s existing helper (`ConsistentRead: true`; throws `"Team not found"` / `"Access denied: caller is not a coach on this team"` / the archived message) and returns `{ team, coaches }`.

   **Archived-team decision (Minor 6):** `requireActive: true` — this Lambda now **enforces server-side** what `docs/SHARING-PERMISSIONS.md` already documents as a rule ("coach access can only be revoked for active teams"), previously only UI-enforced (`Management.tsx`'s Sharing tab is filtered to active teams client-side). Chosen over `requireActive: false` for consistency with the already-documented intent and to close the gap between "documented" and "actually enforced" the same way `createGameSafe` already did for game creation. Accepted tradeoff: if a revoke sweep fails partway through and the team is archived before a retry, the retry is rejected until the team is restored — a rare compound race, noted in Risks, not fixed here.
3. **Scan `TeamInvitation` for this team once** (moved ahead of the `Team.coaches` write this revision — Major 2): `scanByField(teamInvitationTable, 'teamId', teamId, ['id', 'coaches', '#status', 'acceptedBy', 'email'], { '#status': 'status' })`. **`#status` alias required (F1 — Major, architecture review round 3):** `status` is a DynamoDB reserved word; projecting it as a raw field name throws `ValidationException` on every call. The alias and its `ExpressionAttributeNames` entry must be passed exactly as shown, per file #1's F1 fix. `email` is new since round 2 (Major 1) — needed to derive the target's email for step 5 below. This same scan result is reused by step 10's `coaches`-field sweep later — no second scan needed.
4. **Targeted status transition — `TeamInvitation` reversibility close, `ACCEPTED` case (Critical 1):** from the rows fetched in step 3, for each where `status === 'ACCEPTED' && acceptedBy === targetUserId`, conditionally `UpdateCommand` to `status = 'EXPIRED'` guarded by `status = :acceptedStatus` (ignore `ConditionalCheckFailedException` as "already transitioned" — mirrors `archive-team/handler.ts:135-165`'s pending-invitation-expiry pattern exactly, just filtered on `acceptedBy = targetUserId AND status = 'ACCEPTED'` instead of `status = 'PENDING'`). Derive `targetEmail = normalizeEmail(email)` from the matched row(s) (there is normally at most one, but the loop handles more defensively).
5. **Targeted status transition — `TeamInvitation` reversibility close, `PENDING`-by-email case (Major 1):** if step 4 derived a `targetEmail`, from the same rows fetched in step 3, for each where `status === 'PENDING' && normalizeEmail(email) === targetEmail`, conditionally `UpdateCommand` to `status = 'EXPIRED'` guarded by `status = :pendingStatus` (ignore `ConditionalCheckFailedException` — identical pattern to step 4, just a different starting status and matched by email instead of `acceptedBy`).

   **Do NOT use `listInvitationsByEmail` for this (F5 — Minor, must fix, architecture review round 3).** `amplify/data/resource.ts` declares a `TeamInvitation` secondary index, `index('email').sortKeys(['status']).queryField('listInvitationsByEmail')`, that is **not** team-scoped. Querying it here would expire that email's `PENDING` invitations across every team the person is invited to, not just the team being revoked from — a cross-team blast-radius bug. This sweep must filter the already-team-scoped scan results from step 3 (already limited to `teamId = :teamId`) by matching `email` in application code, exactly as described above — never query a global-by-email index for this step.

   **Named residual risk (F3, stated honestly — architecture review round 3):** if step 4 found no `ACCEPTED` row for the target (no email to derive — e.g. the target was the team's creator, or their `ACCEPTED` row was separately deleted), this step is skipped entirely — there is no non-Cognito source for their email, and closing that fully would require the `AdminGetUser`/`USER_POOL_ID` wiring this plan otherwise avoids. This is **not** "nothing to sweep in that case": `sendTeamInvitation` has no already-a-coach guard, so a stray `PENDING` invitation to that coach's own email can exist (sent by mistake or otherwise) and survives revocation, remaining a working self-restore path via the ordinary `PENDING`-accept flow. Accepted as a residual risk, not built around here — see "Central design finding" §3, "Risks and edge cases," and `docs/SHARING-PERMISSIONS.md`.
6. **Build the `Team`-level remove strategy** (bound to `callerSub`, `targetUserId`), implementing all three invariants, re-evaluated fresh on every retry attempt (Critical 2 — see Architecture Decision above for the full race walkthrough):
   - `callerSub` not in current `coaches` → `abort` ("Access denied: caller is not a coach on this team").
   - `targetUserId` not in current `coaches` → `skip` (idempotent no-op — a retried call after a partial prior failure, or a benign double-click/race, still finishes the child sweep below without erroring).
   - removing `targetUserId` would leave `coaches` empty → `abort` ("Cannot revoke the team's last coach. Invite another coach first." — reworded this revision (UI review, Minor) to match this codebase's established guard-rail phrasing convention, "Cannot [action] [object]. [Actionable next step].", e.g. `create-game-safe/handler.ts:71`'s "Cannot schedule a game for an archived team. Restore the team first.").
   - otherwise → `write` with `coaches.filter(id => id !== targetUserId)`.

   Call `updateRecordCoachesWithRetry(docClient, teamTable, team, teamStrategy, updatedAtIso)` against the `Team` table itself — **no `retryReadProjection` argument** (F2 — Major, architecture review round 3) — using the same shared helper and 3-attempt retry as every child record — this is what makes concurrent-revoke-of-different-coaches-on-the-same-team race-safe, not just a pre-check. **Why the projection argument matters here specifically:** if a concurrent conflict resolves this call to `'skip'` (e.g. the other concurrent attempt already removed the target), the retry re-read must return the **full** `Team` record, not an `['id', 'coaches']`-limited stub — `Team.name` is `.required()` in the schema, and a stub returned as-is to the client via `a.ref('Team')` would fail AppSync's non-nullable-field validation, surfacing a spurious "Error: ..." for a revoke that actually fully succeeded. Every child-record call in steps 7–10 below, by contrast, passes `['id', 'coaches']` as `retryReadProjection` (they only ever need to know whether a write happened). The result's `record` (see file #1's return-shape spec) is the `Team` row returned at step 11 — no separate `remainingCoaches` variable is needed (Minor 3; round 1 computed one but never used it).

   **Ordering note (Major 2):** steps 4–5 now run *before* this write, not after. This is what closes Critical 1's reversibility hole for the entire duration of the sweep, not just after it completes — see "Central design finding" §3 and the Architecture Decision's "Not fully atomic" paragraph for the race this closes. **Accepted tradeoff:** if this step `abort`s (last-coach guard, or the rarer concurrent caller-membership-abort case under Critical 2), steps 4–5's writes have already committed — the target's invitation(s) are left `EXPIRED` while the target remains a full coach (the `Team.coaches` write never took effect, so no access is lost). This only closes that invitation's own drift-repair path for a membership that's still fully intact, which is harmless and does not need to be undone.
7. **Unconditional sweep — `TeamRoster`:** `scanByField(teamRosterTable, 'teamId', teamId, ['id', 'coaches'])`; each row swept via `updateRecordCoachesWithRetry(..., retryReadProjection: ['id', 'coaches'])` (F2 — this table only ever needs `id`/`coaches` back, so the narrow projection is passed explicitly rather than omitted) with a shared remove-target-if-present strategy (`skip` if `targetUserId` absent, or if removal would leave `coaches` empty — Minor 9, logged via `console.warn` in the handler, not the shared helper — `write` otherwise).
8. **Unconditional sweep — `FieldPosition`:** `scanByField(fieldPositionTable, 'teamId', teamId, ['id', 'coaches'])`, same remove-strategy shape as step 7. New in round 1 (Minor 7) — gates the same live lineup-position rows `LineupAssignment`/`Substitution`/`PlayTimeRecord` key off; zero additional complexity given the shared helper already exists for `TeamRoster`.
9. **Unconditional sweep — `Game`:** `scanByField(gameTable, 'teamId', teamId, ['id', 'coaches'])`, swept via `withBoundedConcurrency` (concurrency 10, matching `accept-invitation`'s `Game` backfill), same remove-strategy shape as step 7.
10. **Unconditional sweep — `TeamInvitation.coaches`:** reuses the rows already fetched in step 3 (no second scan), same remove-strategy shape as step 7. Position unchanged from round 1 — only the *status* transitions (steps 4–5) moved earlier; this `coaches`-field sweep stays grouped with the other unconditional child-record sweeps.
11. Return the `Team` record captured in step 6 (`a.ref('Team')`, matching `archiveTeam`/`restoreTeam`/`assignTeamOwner`'s return shape).

## Data Model / API Impact

- **New custom mutation:** `revokeCoachAccess(teamId: String!, userId: String!): Team` — `allow.authenticated()`, real authorization enforced in the handler (caller-membership check, re-evaluated on every retry attempt — Critical 2).
- **No new fields, no new models.** The `TeamInvitation.status` transition reuses the existing `EXPIRED` enum value (`amplify/data/resource.ts:416`) — no schema change.
- **Scan strategy — verify GSI existence before implementation (Minor 8).** The original draft asserted, without verifying, that none of `TeamRoster.teamId`, `Game.teamId`, `FieldPosition.teamId`, `TeamInvitation.teamId` has a secondary index. Amplify Gen2 **auto-creates a relationship GSI on the child table for every `hasMany`/`belongsTo`**, which all four of these qualify for, and no Lambda in this repo currently `Query`s one of these relationship indexes — only `Scan`s — so the claim is *unverified*, not confirmed-false. **Required step before writing the handler:** check the generated table definitions (`amplify_outputs.json`, or `aws dynamodb describe-table`/CDK synth output for the deployed tables) for each of the four. If a GSI exists for a given relationship, use `Query` instead of `Scan` for that step, and add the corresponding index ARN(s) to the IAM policy in file #8 (table ARNs alone do not authorize a `Query` against a GSI). If verification confirms no GSI (matching `accept-invitation`'s existing precedent of unindexed `Scan`s against these same tables), proceed with `Scan` as specified above and record the verification result in the handler's code comments so a future reader doesn't have to re-derive it.
- **Explicit revisit threshold (Minor 8):** rather than an open-ended "revisit if this becomes a hot path," this plan adopts `archive-team`'s own documented trigger verbatim: convert `Scan`→`Query` (assuming a GSI is confirmed to exist per the step above) once a team's `TeamRoster`/`Game`/`FieldPosition`/`TeamInvitation` row count exceeds roughly 5,000 items, or any single sweep step is observed to exceed ~3 seconds in practice.
- **No IAM changes to existing Lambdas** — `accept-invitation`'s existing `grantReadWriteData` grants are untouched; the new Lambda gets its own least-privilege grants (see backend.ts changes above), and — unlike the original draft — needs *fewer* grants than a full accept-invitation mirror (`Player`/`Formation`/`FormationPosition` dropped), plus one new table (`FieldPosition`) and one added table (`TeamInvitation`, already declared for other Lambdas' use).

## Risks and Edge Cases

- **Refactor risk to `accept-invitation/handler.ts` (file #3).** This is a heavily-tested (970-line test file), production-critical path. The shared-module extraction is designed to be behavior-preserving and verified by its *existing* test suite passing unmodified — if that bar isn't met during implementation, fall back to duplicating the low-level helpers in the new Lambda instead of touching `accept-invitation` at all. Flag this explicitly for the architecture reviewer: is the extraction worth the touch, or should `accept-invitation/handler.ts` be left alone and the new Lambda simply duplicate `isConditionalCheckFailed`/`getRecordById`/`scanByField`/`withBoundedConcurrency`? Either is defensible; this plan recommends extraction per the repo's own stated intent (Required Follow-Up #6) but the risk should be weighed explicitly, not assumed away.
- **Security-critical caller-membership check (handler step 2's `assertTeamAccess` call, re-checked again at step 6's `Team`-level retry strategy).** Moving off AppSync's model-level `allow.ownersDefinedIn('coaches')` grant onto a Lambda with elevated IAM removes an authorization check that used to be free. The check must not just exist once at the top of the handler — per Critical 2, it must be re-evaluated on every retry attempt of the `Team`-level write, or a concurrent revocation of the caller themselves mid-retry silently bypasses it. This is the single most important thing for the security reviewer stage to verify, and needs its own explicit handler test (item #6, the concurrent-revoke-abort case).
- **Concurrent revoke calls (two different target users, same team, same time) — fixed per Critical 2.** The shared retry helper's strategy is re-evaluated against a freshly re-read record on every attempt, not just once before the loop starts. A naive `contains(coaches, :targetUserId)`-only write condition, retried only on the *removal computation* and not the *guards*, would let two concurrent full-array replacements silently clobber each other into an empty, permanently-inaccessible `coaches` array (walked through in detail in "Architecture decision" above). This plan's fix generalizes the write-time `contains(coaches, :callerSub)` pattern already used by `archive-team`/`assign-team-owner` into the shared helper itself, so every table swept through it gets the same protection "for free," not just the `Team` record.
- **Idempotency (revoking an already-revoked user).** Deliberate behavior change from today: the old client function threw `'User is not a coach of this team'`; the new Lambda treats "target not currently in `team.coaches`" as a `'skip'`/no-op success and still runs the child sweep (so a retried call after a partial prior failure can finish). This is safe because `InvitationManagement.tsx`'s "Remove" button is only ever rendered next to a `userId` that's in the currently-displayed coaches list — the old error path was a defensive backend guard for a race, never the primary UX path, and treating a benign double-click/race as idempotent success is arguably a better outcome than surfacing a confusing error. Flagging as an intentional, documented behavior change for reviewer sign-off, not an oversight.
- **Revoking the team's last coach.** Addressed by the zero-coaches guard (handler step 6, `'abort'` outcome) — new, not in the issue's literal text; re-evaluated per retry attempt per Critical 2, not a one-time pre-check. As of this revision (Major 2), this abort can occur after steps 4–5's `TeamInvitation` status transitions have already committed — see the "Central design finding" §3 tradeoff note and file #4 step 6.
- **Archived-team enforcement (Minor 6).** `requireActive: true` is a new server-side restriction that didn't exist before this plan (previously UI-only). Accepted tradeoff: a partially-failed revoke sweep followed by the team being archived before a retry now requires restoring the team first — a rare compound race (revoke failure + archive, in that order, before the retry), not fixed here, but worth naming since it's a genuinely new failure mode introduced by closing the enforcement gap.
- **`Player`/`Formation`/`FormationPosition` residual access (Critical 3).** A revoked coach retains `coaches`-array access to any `Player`/`Formation`/`FormationPosition` record they still appear on, including ones rostered/used only by the team they were just revoked from, if no provenance data exists to safely decide otherwise. This is a real, accepted, and now-documented gap (`docs/SHARING-PERMISSIONS.md`), not silently dropped — closing it properly requires a `createdBy` field and its own migration plan, out of scope here.
- **`TeamInvitation` reversibility close, updated scope (Critical 1 + Major 1), with two named residual risks from architecture review round 3 (F3, F4).** This plan closes both the reversibility hole in `accept-invitation`'s idempotent-repair branch (an already-`ACCEPTED` invitation for the target on this team, transitioned to `EXPIRED`) **and** any still-`PENDING` invitation to the same email as that `ACCEPTED` row (also transitioned to `EXPIRED`) — see "Central design finding" §3 — **for any target who has at least one `ACCEPTED` invitation row on this team.** Two cases are not closed, documented rather than fixed:
  - **F3 — no `ACCEPTED` row to derive an email from.** A target with no `ACCEPTED` `TeamInvitation` row on this team at all (team creators; anyone whose `ACCEPTED` row was separately deleted) has no email to derive, so no `PENDING`-by-email sweep can run for them. This is **not** merely "nothing to close" — `sendTeamInvitation` has no already-a-coach guard, so a stray `PENDING` invitation to that coach's own email (sent by mistake or otherwise) can exist and survives revocation as a working self-restore path. Closing it fully would require `AdminGetUser`/`USER_POOL_ID` Cognito wiring, deliberately not built in this slice. A brand-new invitation sent to the target's email *after* revocation completes is, correctly, a fresh grant this Lambda has no reason to touch — that part is not a gap.
  - **F4 — true concurrent accept-vs-revoke race.** Reordering the `TeamInvitation` status transitions ahead of the `Team.coaches` write (Major 2) closes the crash/timeout/partial-failure version of the reversibility window, but not a genuine sub-second race: if the target calls `acceptInvitation` on a still-`PENDING` invitation at almost exactly the same moment a coach calls `revokeCoachAccess` on them, the revoke's invitation scan can read the row as still `PENDING`, the accept can land afterward as an ordinary successful transaction, and revoke's expiry write then no-ops harmlessly against the now-stale scan without ever seeing the new `ACCEPTED` status to expire. Accepted as a narrow residual risk given how rare simultaneous accept-and-revoke on the same invitation is; not closed by a second post-write expiry pass in this slice.
  Both are recorded as named residual risks in `docs/SHARING-PERMISSIONS.md` (Docs changes above) and covered as documented-known-gap tests, not closed-behavior assertions, in `handler.test.ts` (file #6).
- **`InvitationManagement.tsx`'s message display has no ARIA live region (UI review round 1, informational — not a regression from this plan).** The single success/error message line documented in the new §7.9 "Sharing & Permissions" subsection (Docs changes above) is a plain `<div>`, not an `aria-live` region, so a screen-reader user isn't automatically notified when a revoke succeeds or fails. Pre-existing on this component before this plan; noted here only because this plan's UI-SPEC edit is already documenting this exact surface. No fix proposed as part of this plan.
- **The distinct owner concept (`Team.ownerId`).** Confirmed via `assign-team-owner/handler.ts` and `docs/SHARING-PERMISSIONS.md`: `ownerId` is separate from `coaches` membership, has no `update` grant (only `assignTeamOwner`/creation can set it), and `revokeCoachAccess` can already orphan an owner (owner removed from `coaches` while `ownerId` still points at them) — a **named, accepted, separately-tracked tradeoff** (Required Follow-Up #7). This plan's new Lambda is the natural future home for that guard (it already does the caller/target membership checks the guard would build on), but implementing it now would silently expand this issue's scope beyond what was asked. Left as a follow-up note in the new handler file's comments (pointing at the tracked follow-up), not implemented.
- **Partial-failure / rollback behavior.** Best-effort per-record, matching `accept-invitation`'s own precedent (see Architecture Decision, "Not fully atomic" paragraph) — not a new gap introduced here. A failure partway through the sweep (e.g. Lambda timeout after `TeamRoster`+`FieldPosition` complete but before `Game`/`TeamInvitation`) leaves `Team.coaches` already correctly updated (the authoritative cutoff already took effect) with the remainder recoverable by simply calling `revokeCoachAccess` again (idempotent per the point above, including the `TeamInvitation` status-transition step, which is itself a conditional, retryable, per-item write).
- **Real-time/subscription staleness (the `Home.tsx` question, resolved — see next section).** Not a gap requiring frontend changes, but not instant either for an already-open session.
- **Scan cost at scale.** Net *lower* scan volume than the original draft (the cross-team `remainingTeams` scan is gone), plus one new table (`FieldPosition`) and one added table (`TeamInvitation`, already scanned by `archive-team` for a different purpose). See "Data Model / API Impact" above for the required GSI-verification step and the explicit numeric revisit threshold (5,000 items / ~3 seconds, matching `archive-team`'s own documented trigger) — no longer an open-ended "revisit if this becomes a hot path."

## Decision: `Home.tsx`'s ungated `Game` query — no change needed

`Home.tsx`'s `useAmplifyQuery('Game', { sort: ... })` (no `filter`) uses `observeQuery` under the hood (`src/hooks/useAmplifyQuery.ts`), which is itself backed by AppSync's standard list/sync operations — already scoped server-side by `allow.ownersDefinedIn('coaches')` on the `Game` model. It was never literally "ungated"; it relies entirely on `Game.coaches` being correct, which is exactly what this plan now guarantees on revoke (previously it was only guaranteed on accept). Once the sweep runs, a revoked coach's *own* subsequent queries (fresh page load, new session) naturally stop returning that team's games — no `Home.tsx` filter change is needed to fix the symptom described in the issue.

**One real, but pre-existing and already-accepted gap:** a coach with an **already-open** browser session at the moment they're revoked won't see their `Game` list update until they reload or their `observeQuery` subscription naturally resyncs — this Lambda writes via the raw DynamoDB SDK (bypassing AppSync mutations), exactly like `archiveTeam`/`restoreTeam`/`assignTeamOwner` already do, and `docs/SHARING-PERMISSIONS.md`'s "Known residual risks" already documents this exact class of staleness for those three Lambdas ("write via the DynamoDB SDK directly and never trigger an AppSync subscription event"). This plan does not introduce a new instance of that gap; it's the same accepted characteristic, now also true for revocation. No `Home.tsx` change proposed to close it — consistent with how the archive/restore/assign-owner case was left as a documented, accepted characteristic rather than fixed.
