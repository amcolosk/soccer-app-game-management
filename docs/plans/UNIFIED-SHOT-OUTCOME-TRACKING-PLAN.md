# Unified Shot-Outcome Tracking (replaces separate Goal/Shot/Save entry)

Status: Draft — revised after architecture review round 1 (A1–A4 dedup-state hardening, M1 edit-modal guardrail fix, m3–m10 and i4 folded in; two factual errors in the original Q1 writeup corrected) — ready for re-review, then UI review for the items explicitly flagged below.
Date: 2026-09-24 (revised 2026-09-24)
Risk tier: **Tier 2** (stated explicitly per the orchestrating thread's instruction, not re-derived from `classify:risk-tier`, which only reports Tier 0 pre-implementation because no diff exists yet). Reasons: touches `amplify/data/resource.ts` (schema change to `Shot` + `submitStatEvent`'s arguments) and `amplify/functions/submit-stat-event/**` (Lambda logic change to the app's only unauthenticated write path) — both on the dev-pipeline skill's hardcoded Tier-2 path list. It also changes the idempotency/dedup contract of a guest-writable Lambda, which is a security/data-integrity-relevant change in its own right.

## Background / resolved design (not up for relitigation)

Today `Goal`, `Shot`, `Save` are three independent models with three independent entry points (coach-side: `GoalTracker.tsx` + `ShotSaveTracker.tsx`, switched by `StatsSubViewTabs.tsx`'s Goals/Shots/Saves segmented control; helper-side: `StatTrackerView.tsx`'s 3-way GOAL/SHOT/SAVE tap grid + `submitStatEvent`). A coach or helper has to remember, unprompted, to log correlated events (tap Shot AND Goal for a shot that scores). No production `Shot` rows exist yet, so `Shot`'s shape is free to change with zero migration concern; `Goal` and `Save` have real historical data and are **not** changing shape.

Replacement design (already agreed with the user):
- Exactly **two entry points**: "Log Shot – Us" / "Log Shot – Them" (mirrors the existing `btn-stat-us`/`btn-stat-opponent` pattern).
- "Us": pick shooter (skippable) → pick outcome (**Goal / Saved / Blocked / Wide**) → if Goal, optional assist picker; if Saved, no keeper attribution possible (no opponent roster) — plain confirm.
- "Them": no shooter step → pick outcome → if Saved, auto-prefill the current on-field goalkeeper (reuse `getCurrentGoalkeeperId`/`computeActiveGoalkeeperId`, don't reimplement), overridable via the existing "pick another keeper" escape hatch.
- One submission writes whatever combination of records the outcome implies:
  - **Every outcome always writes a `Shot` row** (attributed to the shooter when "Us" and known).
  - **Goal** also writes a `Goal` row (scorer/assist only on the "Us" side).
  - **Saved** also writes a `Save` row (keeper attribution only when "Them" shot + our keeper saved it).
  - **Blocked**/**Wide** write only the `Shot` row.
- Identical outcome→records mapping on both surfaces (coach live-game screen and the public `/track/:token` helper page + `submitStatEvent`).
- `Shot.onTarget: boolean` → `Shot.outcome: a.enum(['GOAL','SAVED','BLOCKED','WIDE'])`. `Goal`/`Save` shapes unchanged.
- **Decision (per the user's own lean, confirmed here, no concrete need found to override it): no new FK between `Shot` and `Goal`/`Save`.** They remain unlinked siblings written together atomically from one user action, exactly as today. See "Accepted risk: sibling drift" below for what this costs.

## Critical technical risk this plan must solve explicitly (flagged per the task's own ask)

`submitStatEvent` now writes **up to two** records per invocation (`Shot` always, plus `Goal` or `Save` conditionally) through two independent AppSync mutations — there is no multi-table transaction available to it (it must stay on `generateClient<Schema>({ authMode: 'iam' })`, not raw DynamoDB SDK, so the coach's `observeQuery` subscription still fires — CLAUDE.md's standing constraint). If the first write (`Shot`) succeeds and the second (`Goal`/`Save`) throws, the existing dedup pattern's blanket "release the claim on any throw" behavior would let a client retry with the same `clientEventId` re-run the **entire** pipeline from scratch — re-writing a **duplicate `Shot` row**. This is a real, not theoretical, regression risk introduced by going from 1 write to 2, and is called out explicitly below rather than solved by a copy-paste of the existing single-write dedup code.

### Recommended design: resumable dedup state (no new unverified Amplify assumption)

**Architecture review has approved this design as the primary mechanism.** Extend the existing dedup row (still stored in the `FanViewRateLimit` table, same `{limiterKey: 'dedup#<clientEventId>', minuteBucket: 'dedup'}` identifier and ~10-minute TTL) with a third status and a small persisted write-context:

- `status: 'pending' | 'shot-written' | 'succeeded'` (was `'pending' | 'succeeded'`) — `'resuming'` is also used transiently, see A2 below.
- On first claim (`status` didn't exist → claimed 'pending'): run the full validate → select-game → validate-players pipeline. **Persist `writeContext` (fields listed below) immediately after validation/derivation completes, before the `Shot` write is even attempted** — this is a deliberate tightening over an earlier draft of this plan, which persisted `writeContext` only right before the second write; see A1 for why the earlier point was too late. Then create `Shot`.
  - If `outcome` is `BLOCKED`/`WIDE` (nothing more to write): mark `succeeded`, done — identical shape to today's single-write case.
  - If `outcome` is `GOAL`/`SAVED`: once the `Shot` write returns success, set `status: 'shot-written'` (the `writeContext` needed to resume is already persisted from the step above). Then attempt the `Goal`/`Save` write.
    - Success → mark `succeeded`, return `{ok:true}` (unchanged shape).
    - Throw → **do not release/delete the dedup row** (this is the one deviation from today's outer catch-all "release on any throw"). Return `{ok: false, reason: 'PARTIAL_WRITE'}` (see m4 below — not a thrown error) so the row stays at `shot-written`, bounded by the same TTL as before.
- On a later claim attempt finding `status === 'shot-written'`: **resume**, per A2/A3 below — atomically re-claim the row, skip validation/selection/`Shot`-write entirely (already done), reconstruct the `Goal`/`Save` create call from the persisted `writeContext`, and attempt only that. This deliberately does **not** re-check `GAME_NOT_LIVE`/`GAME_CHANGED`/roster-membership against current game state — those were already satisfied by the original attempt, and re-validating against a game that has since moved on (paused, halftime, completed) must not permanently orphan an already-committed `Shot` row. On success, mark `succeeded`; on throw, leave (or restore) at `shot-written` again (still resumable until TTL), respecting A1's progress-based release rule.
- `status === 'pending'` on a claim attempt still means "a genuinely concurrent, same-instant request is mid-flight" → `concurrent-duplicate`, unchanged.

#### Hardening the state machine (architecture review Q1 amendments A1–A4 — all required, not optional)

- **A1 — release based on progress made, not on exception type.** Release/delete the dedup row **only** based on whether *any model write has returned success this invocation* — track this with a local `progressMade` boolean in the handler, set `true` the instant `Shot.create`, `Goal.create`, or `Save.create` returns success. Do **not** decide by pattern-matching a `PartialWriteError` exception class, which misses two real failure modes: (a) the `Shot` write itself succeeds, but the immediately-following `status: 'shot-written'` `UpdateCommand` then throws — that's not a `PartialWriteError`, so the naive design would still wrongly release the row and let a retry duplicate the `Shot`; (b) on the resume path, the `Goal`/`Save` write succeeds but the follow-up `markDedupSucceeded` call throws — if that reaches a releasing `catch`, a retry re-runs everything and duplicates both records. **Invariant: once any model write has returned success this invocation, never delete the row on any subsequent error — only TTL expiry may ever clear a row past that point.** This is exactly why `writeContext` must be persisted before the `Shot` write, not only before the second write: it must exist before the earliest point past which the row becomes non-releasable, so a resume from that point is always reconstructible.
- **A2 — atomic re-claim on resume.** The resume path must re-claim the row via a **conditional** `UpdateCommand` (`ConditionExpression` requiring `status = 'shot-written'`, transitioning it to `'resuming'`), not a plain read-then-write. If the condition fails (another invocation already moved the row), return `concurrent-duplicate` and do not attempt the write. If the resumed write then fails, conditionally set the status back to `shot-written` (so a future retry can still resume) rather than leaving it stranded at `'resuming'`. Without this atomic re-claim, two concurrent retries can both read `shot-written` and both attempt the `Goal`/`Save` write, duplicating it.
- **A3 — resume trusts only persisted state.** The resume path must read **only** the persisted `writeContext` and must ignore every request argument except `clientEventId` (used solely to locate the row) — this is precisely what makes skipping validation/game-state checks on resume safe, since nothing about the resumed write depends on what the retry request happens to say. **Add a test**: a resume request whose `clientEventId` matches an existing `shot-written` row but whose `outcome`/`playerId`/`assistPlayerId`/`keeperPlayerId` arguments differ from the original request still writes the **persisted** `writeContext` values, not the new request's values.
- **A4 (= m3) — re-read `coaches` fresh at resume, never cache it.** `writeContext` persists `teamId`, not a copy of `coaches`. At resume time, fetch the team record fresh via a `GetCommand` and use its *current* `coaches` array for the `Goal`/`Save` write. This matches both the handler's own existing comment on why `coaches` is read fresh (`handler.ts:272-275`) and CLAUDE.md's standing rule that `coaches[]` must always be sourced live from the team record, never cached/copied: a co-coach could accept a team invitation in the window between the original partial failure and the eventual resume, and a `coaches` copy taken at the original attempt would silently lock that co-coach out of the resumed `Goal`/`Save` row.

`writeContext` (persisted right after validation/derivation, before the `Shot` write) therefore holds: `teamId` (not `coaches`), `gameId`, `gameSeconds`, `half`, `timestamp`, `outcome`, `forUs`, `playerId`, `assistPlayerId`, `keeperPlayerId` — everything needed to reconstruct the `Goal`/`Save` write and the shared `gameId`+`timestamp`+`gameSeconds` correlation (see i4) without re-deriving or re-trusting anything from the resumed request.

This requires no assumption about Amplify's exact conditional-create-on-client-supplied-id error surface. **Correction to this plan's original claim**: an alternative, simpler design — a deterministic `clientEventId`-derived id on the `Goal`/`Save` write (e.g. `helper:<clientEventId>:goal`) plus create-then-treat-duplicate-error-as-success — was considered and is not the primary recommendation here, but this plan previously and incorrectly asserted "zero in-repo precedent" for that class of pattern, based on a `.create({ id:` grep that missed the real precedent. Architecture review corrected this: real precedent for deterministic-id-based writes already exists in this codebase — `GameManagement.tsx:93-101`'s `buildDeterministicStartPlayTimeRecordId` (used at ~line 1524, ~line 1733), `useOfflineMutations.ts:258-285`'s create-with-duplicate-id-treated-as-success handling (tested at `useOfflineMutations.test.ts:236` and `:722`), and a client-generated id for `QueuedSubstitution` at `GameManagement.tsx:1908-1918`. **This does not change the ruling** — resumable dedup state remains the required primary mechanism for this plan — but a deterministic-id approach for the Lambda's `Goal`/`Save` write is worth recording as **optional future hardening, explicitly deferred and not required for this plan**, with two caveats for whoever picks it up later: the Lambda would need its own duplicate-error-detection logic (it can't import `useOfflineMutations.ts`'s implementation from `src/`), and a "get on error" variant can't work as specified today because the schema-level `allow.resource(submitStatEvent)` grant (`resource.ts:1092`) is `mutate`-only, not `query` — the Lambda's IAM role has no read grant on `Goal`/`Save` to fall back to.

#### Why shot-first, not goal-first (i4 / architecture review)

The write order (`Shot` always first, `Goal`/`Save` second) is deliberate, not incidental, and this reasoning belongs in the plan, not only in review notes: if a helper sees an error and manually re-logs the same event, a duplicated `Shot` only pollutes analytics (an extra row the coach can see and delete in the Shots list), whereas a duplicated `Goal` would corrupt the live score itself (`Game.ourScore`/`opponentScore` derivation, per `score.ts`'s `computeScoreFromGoals`) — a strictly worse failure mode. Writing the lower-stakes record first and gating the higher-stakes record behind resumable state means the worst *uncorrected* outcome is an orphaned `Shot`, never a duplicated `Goal`.

**Bounded accepted gap (corrected):** the real exposure window for an orphaned `Shot` (a `Shot` whose `outcome` is `GOAL`/`SAVED` but has no backing `Goal`/`Save` row) is **not** the 10-minute dedup TTL — it is however long the helper's tap-flow sheet stays open. `clientEventId` lives only in that sheet's in-memory state and is discarded the moment the sheet closes (`closeFlow`) or a non-LIVE poll arrives (within roughly the ~12s poll interval); a fresh `clientEventId` on any later retry starts an unrelated new dedup row, so the dedup TTL is largely moot to this particular gap. If the helper doesn't retry within that in-memory window, the orphan is effectively permanent from the app's perspective. This is more than an analytics nuisance when the missing record is a `Goal`: **an orphaned "Us" `Goal` (Shot says `GOAL`, no backing `Goal` row) means the live score is visibly missing a goal on both the coach's and the fans' views**, until a coach happens to notice the discrepancy in the Shots list and manually corrects it. It remains a data-quality gap, not corruption, and stays in the same accepted-risk category as "Accepted risk: sibling drift" below — but its user-visible severity (a wrong scoreboard, not just an analytics blind spot) is worth stating plainly rather than downplaying, which the plan's original wording ("data-quality nuisance ... not corruption") did not do clearly enough.

### Coach-side (authenticated) path gets a lighter-weight treatment

`useOfflineMutations.ts`'s `createShot`/`createGoal`/`createSave` are independent, separately-queued mutations (each goes through its own `enqueueOrRun` call) — if offline, both a `createShot` and a follow-on `createGoal`/`createSave` call get queued and flushed independently by the existing offline-queue retry logic, which already tolerates one succeeding before the other. The realistic failure mode (an authenticated, non-guest write to the coach's own AppSync API, immediately visible to the coach who has full Edit/Delete affordances on both `Shot` and `Goal`/`Save`) does not warrant the same resumable-state machinery as the anonymous, no-UI-recourse helper path. Plan: sequence `mutations.createShot(...)` then, if applicable, `mutations.createGoal(...)`/`mutations.createSave(...)`; if the first throws, surface the existing generic failure message and stop (nothing written).

**Fix required (m5 — architecture review): the original "log it manually" recovery message doesn't work.** If the first (`Shot`) succeeds but the second (`Goal`/`Save`) throws, the plan previously proposed telling the coach to "check the Shots list and log it manually if needed" — but once the separate Goal-only/Shot-only/Save-only entry buttons are removed, there is no manual entry path left to follow; that advice is dead. Instead: on a second-write failure, **keep the entry modal open** and show a **"Retry saving goal/save"** action that re-sends only the already-derived `Goal`/`Save` payload (computed once from `deriveShotOutcomeWrites` at submit time, cached in component state) — the `Shot` already succeeded and must not be re-sent. Never tell the coach to "re-log" the event; the retry action must resume from where it left off, mirroring (at a much lighter weight, since there's no dedup/idempotency concern on an authenticated single-user write) the same "don't repeat completed work" principle as the helper-side resumable design above. This asymmetry (helper gets server-side idempotency machinery; coach gets a client-side "retry the second write" affordance, not a server-side resumable state machine) remains intentional and should be called out to whoever reviews this, not silently inconsistent.

## Accepted risk: sibling drift (no FK, by design)

Because `Shot`/`Goal`/`Save` stay unlinked siblings, any independent edit or delete on one side can now visibly diverge from the shot-outcome story that created it — e.g. deleting a `Goal` row leaves a `Shot` row with `outcome: 'GOAL'` and no backing `Goal`; editing a `Shot`'s shooter doesn't update a same-event `Goal.scorerId` or vice versa. This already existed in a smaller form today (two independent taps could already go out of sync); unifying entry widens the surface where it's *expected* the two move together, without actually enforcing it. Given the explicit user direction to lean away from adding a new relationship absent a concrete need, and that a coach retains full visibility/Edit/Delete on every affected list to manually reconcile a mismatch, this plan accepts the drift rather than building cross-model cascade logic.

**Guardrail (M1 — architecture review Major finding, corrected design):** the plan's original wording — "the Shot edit modal's outcome control, if kept, should only offer `BLOCKED`/`WIDE`" — is broken as written. Today `ShotSaveTracker.tsx:146` seeds the edit modal's outcome state from the item's *current* stored value, and `:165-168` **always** sends that field on `updateShot`. Combining "dropdown restricted to Blocked/Wide" with "outcome optional on update" means editing the *shooter* on a `GOAL`- or `SAVED`-outcome Shot would silently send `outcome: 'BLOCKED'` (or whatever the restricted dropdown's default value is) on that update — corrupting the exact outcome the guardrail exists to protect, the opposite of its intent.

**Required fix:** the edit modal must show an **editable** outcome control **only** when the Shot's current outcome is `BLOCKED` or `WIDE`. When the current outcome is `GOAL`, `SAVED`, or `null`, show a **read-only label** instead (e.g. "GOAL — delete and re-log to change the outcome"), with no editable dropdown. The `updateShot` payload must **omit `outcome` entirely** unless the editable control was shown *and* its value was actually changed from the seeded value — never send a field the coach never had the ability to meaningfully edit. Correcting a genuinely wrong Goal/Saved outcome remains delete-and-re-log through the unified entry flow, never an in-place outcome edit. **Add a test**: "edit shooter on a GOAL-outcome shot keeps outcome GOAL" (i.e. asserts `updateShot` is called without an `outcome` key, or with the unchanged value, when the edit modal is opened on a GOAL row and only the shooter field is changed).

**Delete-confirmation copy (i4):** since the sibling-drift risk means deleting a `Goal`/`Save` row leaves its originating `Shot` row behind unchanged, the `Goal`/`Save` delete confirmation dialogs should say so explicitly — e.g. "The matching shot stays in the Shots list" — so the coach isn't surprised by an apparently-orphaned Shot row afterward. This is a no-schema-cost UX note tied to the accepted sibling-drift tradeoff, not a behavior change.

## New shared pure module (mirrors the `gameClock.ts`/`goalkeeper.ts`/`score.ts` pattern)

The "outcome → which records to write, with what values" mapping is exactly the kind of logic CLAUDE.md says must be a single pure module with a Lambda-side twin (a Lambda can't import from `src/`):

- `src/utils/shotOutcomeMapping.ts` (new, coach-side):
  ```ts
  export type ShotOutcome = 'GOAL' | 'SAVED' | 'BLOCKED' | 'WIDE';
  export interface ShotOutcomeInput {
    forUs: boolean;
    outcome: ShotOutcome;
    playerId?: string | null;       // shooter ("Us" only) -- also becomes Goal.scorerId on GOAL
    assistPlayerId?: string | null; // "Us" + GOAL only
    keeperPlayerId?: string | null; // "Them" + SAVED only -- our keeper
  }
  export interface DerivedShotWrites {
    shot: { takenByUs: boolean; outcome: ShotOutcome; playerId: string | null };
    goal: { scoredByUs: boolean; scorerId: string | null; assistId: string | null } | null;
    save: { byUs: boolean; playerId: string | null } | null;
  }
  export function deriveShotOutcomeWrites(input: ShotOutcomeInput): DerivedShotWrites { /* ... */ }
  ```
  Key derivations to get right (verified against `Goal.scoredByUs`/`Save.byUs`'s existing documented semantics):
  - `shot.takenByUs = forUs`; `shot.playerId = forUs ? (playerId ?? null) : null`.
  - `goal` populated iff `outcome === 'GOAL'`: `scoredByUs = forUs` (an "Us" shot that goes in is our goal; a "Them" shot that goes in is their goal — **not** inverted), `scorerId`/`assistId` only when `forUs` (opponent goals carry no scorer, matching today).
  - `save` populated iff `outcome === 'SAVED'`: `byUs = !forUs` — **inverted relative to the shot's own side**, because a "Us" shot being Saved means the *opponent's* keeper made the save (`byUs: false`), and a "Them" shot being Saved means *our* keeper made it (`byUs: true`). `playerId` (keeper) only ever populated on the `!forUs` branch (our keeper), from `keeperPlayerId` — never on the `forUs` branch, since there's no opponent roster to attribute to (matches the background spec's "no keeper attribution is possible" for that direction exactly).
- `amplify/functions/shared/shotOutcome.ts` (new, Lambda-side twin, identical logic, can't import `src/`).
- `amplify/functions/shared/shotOutcome.test.ts` (new, parity test, same format as `goalkeeper.test.ts`: an `it.each` table exercising every `{forUs, outcome, playerId, assistPlayerId, keeperPlayerId}` combination, asserting both modules agree).

Both `submitStatEvent`'s handler and the new coach-side entry component call this instead of re-deriving the branch logic inline.

**Explicit, tested invariant (i4):** on both surfaces, the `Shot` and its (optional) `Goal`/`Save` sibling must share the **identical** `gameId` + `timestamp` + `gameSeconds` triple — computed/derived exactly once per submission and reused for whichever record(s) get written, never recomputed per-write (a second `new Date().toISOString()` call for the second write would silently break this). On the Lambda's resume path in particular, the resumed `Goal`/`Save` write must use the `timestamp` **persisted in `writeContext`** from the original attempt, not a freshly-generated one — the whole point of resuming is that the `Shot`'s timestamp already reflects when the event actually happened. This costs nothing schema-wise (no FK is added) but gives a reliable soft correlation key for analytics or any future cascade logic. Add test coverage for this on both the parity test and `handler.test.ts`'s resume scenario.

**Optional reuse suggestion, not required (m10):** the "Us → shooter → outcome → (Goal) assist" and "Them → outcome → (Saved) confirm keeper" step sequences are identical in shape on both surfaces. A small pure transition-state helper in `src/utils`, shared by `StatTrackerView.tsx` and `ShotOutcomeEntry.tsx`, could avoid encoding the same step-sequence state machine twice. This is a nice-to-have for the coding agent to consider during implementation, not a requirement of this plan.

## Data model impact summary

- `Shot`: field replacement (`onTarget: boolean` → `outcome: enum`), no new relationships, no migration needed (zero production rows).
- `Goal`, `Save`: no shape change; new write-time trigger paths only (via the shared mapping module), same fields as today.
- `submitStatEvent`: argument shape change (`eventType`+`onTarget` → `outcome`; new `keeperPlayerId`), and an internal dedup-state-machine change (2 statuses → 3, plus a persisted `writeContext`) — no schema-visible change beyond the mutation's own arguments (the dedup row lives in the existing `FanViewRateLimit` table, already schema-flexible/untyped at the DynamoDB level for this Lambda's own bookkeeping use).
- No changes to `ShareLink`, `FanViewRateLimit`'s *schema declaration*, `getFanGameView`, or `getStatTrackerView`.
- `coaches[]` population: unaffected — every new/changed write path (`ShotOutcomeEntry.tsx`'s `mutations.createShot/createGoal/createSave` calls, and `submitStatEvent`'s Lambda-side creates) already sources `coaches` from `team.coaches` exactly as the code being replaced does today; no new record-creating path introduced that skips this.

## Edge cases (beyond the two flagged above as their own sections)

- **`outcome` is nullable in the generated TypeScript type** even though every new write always populates it (an `a.enum()` field can't be `.required()` at the schema level) — any UI code rendering `shot.outcome` should handle `null`/`undefined` defensively (e.g. "Unknown outcome") rather than assuming one of the 4 values or silently defaulting to a guess; this should be unreachable in practice given zero legacy rows, but must not crash if a row is ever hand-edited via the console.
- **Skipped shooter/keeper on "Us"+Goal (Q2/Q3 — RESOLVED, option (a), scope-corrected per architecture review's m7)**: if a coach/helper skips the shooter picker on a "Us" shot that then resolves to Goal, the resulting `Goal` row has no `scorerId` — identical to today's existing "Us Goal with no scorer selected" case (already handled: `GoalTracker`'s own create-goal validation currently *requires* a scorer for a "Us" goal — `if (goalScoredByUs && !goalScorerId)`). **Scope correction (m7): this is not Goal-only.** `ShotSaveTracker.tsx:94-97` shows coach-side "Us" **Shots** also currently require a shooter today (`if (statView === "shots" && entryIsUs && !entryPlayerId) { showWarning(...); return; }`), independent of the Goal-specific check. The unified flow relaxes **both**: the shooter step is skippable up front for a "Us" entry regardless of what outcome it later resolves to (Goal, Saved, Blocked, or Wide) — a behavior change from today's coach-side validation on *both* `GoalTracker` and `ShotSaveTracker`, though it already matches the *helper*-side `StatTrackerView.tsx`'s existing "every event type's playerId is optional" stance. **Resolved by architecture review: option (a)** — shooter stays skippable throughout, consistent with the background spec's "pick shooter (skippable)... then pick outcome" ordering; a scorer-less "Us" Goal or a shooter-less "Us" Shot are both accepted, user-visible behavior changes from today. Both relaxations (Goal AND Shot no longer requiring a shooter up front) must be recorded in the `docs/specs/UI-SPEC.md` §7.4 update (item 23 below), not just the Goal one.
- **`GAME_NOT_LIVE`/`GAME_CHANGED` mid-flow on the helper page**: unaffected by this change — those checks still run identically before any write is attempted (or, on a resumed partial-failure, are deliberately skipped per the resumable-state design above).
- **Rate limiting**: unaffected — `checkRateLimits`'s write-dimension ceiling is still consulted once per invocation (inside `runCore`, before any write), regardless of whether that invocation ends up performing 1 or 2 model writes.
